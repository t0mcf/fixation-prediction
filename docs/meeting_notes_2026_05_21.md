## what the model is supposed to do 

given an image and the fixations the viewer has made so far, predict where they will look next — as a probability heatmap over the image.

so it's a conditional scanpath model. not just "where is salient" (that would be a saliency map model) but "given that you've already been looking HERE and HERE and HERE, where do you go next." that conditioning on history is the whole point.

---

## the data

- ~20.5M synthetic scanpaths, generated by an **active inference model** on ImageNet images
- each scanpath: up to 16 fixations, stored as (x, y) ∈ [-1, 1]² (normalized image coordinates)
- split by IMAGE (not by scanpath) → clean train/val/test split, no image leakage
- stored in parquet, loaded lazily with the dataloader
- training set: I use 200k images with 16 scanpaths each = 3.2M scanpaths per epoch
- val set is everything in val split, ~16k batches at bs=128 but I only use the first 400 batches per epoch to keep validation fast

---

## architecture — top level

```
image (224×224) 
  → frozen DINOv2 ViT-B/14
  → 256 patch tokens, dim=768 each
  → image adapter (Linear 768→256 + LayerNorm)
  → [optional: learned 2D patch pos embeddings]
  → image tokens (256, 256)

prefix fixations (up to 15 fixations, each (x,y))
  → coord_proj (Linear 2→256) + learned positional embeddings
  → 2-layer causal transformer
  → scanpath tokens (T, 256)

image tokens + scanpath tokens
  → 4× cross-attention fusion layers
  → fused image tokens (256, 256)

fused image tokens
  → reshape to 16×16 grid
  → conv decoder (3 conv layers + 2× upsample each)
  → 64×64 logit map
  → log_softmax over 64×64 = 4096 locations
  → log-probability heatmap
```

d_model = 256 throughout. that's the "width" of our representation after compression from DINOv2's 768.

---

## component 1: DINOv2 encoder

- ViT-B/14: vision transformer, base size, patch size 14px
- with 224×224 input → 16×16 = 256 spatial patches
- each patch encoded as 768-dim vector
- **fully frozen** — no gradients, runs under `torch.no_grad()`
- I call `.eval()` explicitly every forward pass just to be safe (BN/dropout behavior)

**why freeze it?**
- DINOv2 has excellent visual representations already — trained on 142M images with self-supervised learning
- if I fine-tune it, I need a much lower LR to avoid destroying the pretrained features (catastrophic forgetting)
- keeping it frozen makes our effective model much smaller (only ~8M trainable params instead of 93M), faster to train, less likely to overfit
- also frees me from worrying about the encoder during the cross-attention experiments

**why DINOv2 specifically?**
- strong semantic + spatial features, known to work well for dense prediction tasks
- `dinov2_base` is the mid-range option (vs. `large` which would be 4× slower, probably not justified here)

**the paths_per_image optimization:**
in the grouped sampler, each batch contains 16 scanpaths for the same image before moving to the next image. so I only run DINOv2 on the unique images (`B // 16` instead of `B`), then tile the result with `repeat_interleave`. gives ~16× speedup on the encoder which is otherwise the bottleneck.

---

## component 2: image adapter

just `nn.Linear(768, 256) + nn.LayerNorm(256)`.

- reduces DINOv2's 768-dim tokens to our working d_model=256
- LayerNorm stabilizes the input to the rest of the network
- this is trainable — it's where we "teach" the projection to align with our coordinate space

**note on patch position embeddings (ablation running):** the problem is that the adapter — a single Linear(768→256) — has to compress BOTH semantic content AND spatial position from the frozen DINOv2 tokens simultaneously. there's no guarantee that spatial position survives this compression in a form compatible with how the scanpath encoder represents fixation coordinates. in cross-attention, for patch at grid position (3,7) to attend strongly to a fixation near (3,7), those two 256-dim representations need to be spatially compatible — but they come from completely independent sources with no coordination.

`--patch-pos-embed` adds a dedicated learnable lookup table on top of the adapter output: `nn.Embedding(256, 256)`, one 256-dim vector per patch, trained end-to-end with our loss. 0 = top-left, 255 = bottom-right, row-major. the adapter can focus on semantic content; position is handled separately. because `patch_pos_embed` and `coord_proj` are both trained with the same objective they can co-adapt until image patch positions and fixation coordinates are spatially compatible in cross-attention. currently running: train_200k_ll_patchpos_15ep.

## component 3: scanpath encoder

takes the prefix (past fixations) and produces scanpath tokens.

input: (B, T, 2) — T = max_seq_len - 1 = 15 fixation coordinates in [-1,1]²

```
coord_proj: Linear(2 → 256)        # projects (x,y) to d_model
pos_embed:  Embedding(15, 256)     # learned position in sequence (step 0, 1, ..., 14)

x = coord_proj(prefix) + pos_embed(positions)

# 2-layer transformer encoder with:
# - causal mask: token t cannot attend to tokens t+1, t+2, ...
# - padding mask: tokens beyond the actual prefix length are masked
```

**why causal mask?** this is critical for the predict-all training trick. in a single forward pass I predict ALL 15 next fixations simultaneously. for this to be valid, the prediction at step t can only use fixations 0..t as context. the causal mask enforces this — it's the same idea as in causal language models (GPT etc.). without it, prediction at step 0 would "see" future fixations and the whole thing would be cheating.

**why learned pos embeddings instead of sinusoidal?** with 20.5M scanpaths the network has plenty of data to learn meaningful position-specific features. sinusoidal would be a prior; learned gives more flexibility. in practice the difference is probably small.

**why only 2 layers?** the prefix is short (max 15 tokens) and the temporal relationships are relatively simple (this is not natural language). 2 layers seems enough; more adds parameters without clear benefit.

## component 4: cross-attention fusion

this is where image and scanpath information get combined.

**unidirectional (baseline):**
- image patches are **queries**, scanpath tokens are **keys + values**
- so each image patch asks "which past fixations are relevant to me?"
- output: updated image tokens (the image patches now carry history-conditioned features)
- scanpath tokens don't change through the fusion — they're computed once and kept fixed

4 layers. each layer:
```
attn_out = CrossAttn(Q=image, K=V=scanpath, key_padding_mask=padding_mask)
# zero out attn_out for samples where ALL scanpath tokens are padding (edge case: first fixation)
image = LayerNorm(image + attn_out)
image = LayerNorm(image + FFN(image))
```

**why image queries scanpath, not the other way around?** the decoder only reads the image tokens at the end. so the image tokens need to be enriched with history information. the scanpath tokens don't go to the decoder, so updating them (in the unidirectional case) would be wasted effort.

**the all-padding edge case:** for the very first prediction (t=0), the prefix length is 0 or 1 (only the initial fixation). in that case all padding mask positions are True → the attention would attend uniformly (or produce garbage if softmax of -inf). I detect this with `all_padding = padding_mask.all(dim=1)` and zero out the cross-attention output, making the model fall back to pure visual saliency for that step.

**bidirectional (new experiment):** parallel co-attention — both directions at once, using PRE-update values. inspired by LXMERT (Tan & Bansal, 2019) / ViLBERT (Lu et al., 2019). scanpath tokens also get updated via a scan←image cross-attention stream. the key is that both streams compute their attention outputs from the SAME (pre-update) tokens as K,V — otherwise you'd have an asymmetric update order. scanpath tokens now carry updated representations across all 4 fusion layers. doubles the parameter count of the fusion module (~6M vs ~3M).

**crashed with CUDA OOM (backward pass, job 13884293).** root cause: bidir fusion keeps gradients flowing through BOTH the image and scanpath token streams across all 4 layers, roughly doubling the activation memory in the backward pass vs. unidirectional. with B=128, the A100 hit 37.7/39.5 GB and couldn't allocate another 1.88 GB. fix options: (1) reduce batch size to 64 — simplest, no code changes, but makes comparison with other runs slightly unfair; (2) gradient checkpointing on fusion layers — recompute activations during backward instead of storing them, ~20-30% more compute but keeps B=128 and exact same training dynamics.

## component 5: decoder

takes the fused image tokens → predicted heatmap.

```
(B, 256, 16, 16)   # reshape patch tokens to 2D grid
→ Conv(256→256, 3×3) + GroupNorm + GELU     # 16×16
→ Upsample(2×, nearest)
→ Conv(256→128, 3×3) + GroupNorm + GELU     # 32×32
→ Upsample(2×, nearest)
→ Conv(128→64, 3×3) + GroupNorm + GELU      # 64×64
→ Conv(64→1, 1×1)                           # 64×64 logits
```

then: `log_softmax` over all 64×64 = 4096 locations → **log-probability heatmap**

**why GroupNorm instead of BatchNorm?** with batch size 128 and the predict-all tiling (×15 = effective 1920 items) I could use BN, but GroupNorm doesn't depend on batch statistics and is more stable during val (single-sample inference). standard choice for spatial tasks.

**why upsample + conv instead of transposed conv?** transposed convolutions with stride 2 produce checkerboard artifacts (the kernel repeats periodically with no overlap). upsample + regular conv avoids this entirely. standard practice since ESRGAN et al.

**decoder dropout (important fix):** originally I had Dropout2d at the same rate as the rest (0.1). but Dropout2d zeroes ENTIRE channels at 64×64 resolution — that's a huge chunk of spatial information to randomly kill. much more aggressive than what the name "0.1" suggests. I added `--decoder-dropout` as a separate knob and set it to 0.0 for the current runs. dropout in the rest of the model (fusion FFNs, scanpath encoder) stays at 0.1.

## predict-all training (the main engineering trick)

**naive approach:** for each of T=15 prediction steps, run a separate forward pass with prefix of length t. 15× more compute.

**predict-all:** one forward pass, all 15 steps simultaneously.

how:
1. encode image once → image_tokens (B, 256, 256)
2. encode full prefix once → scan_tokens (B, 15, 256)
3. tile: image_tiled (B×15, 256, 256), scan_tiled (B×15, 15, 256)
4. compute eff_len[b,t] = min(prefix_len[b], t+1) — encodes BOTH "only see tokens up to step t" AND "clip to actual sequence length"
5. run fusion on the tiled batch (1920 items) → all predictions in one batched forward
6. reshape back to (B, 15, 64, 64)

**why does the causal mask matter here?** eff_len is the key — for the copy of step t, only tokens 0..t are visible. this is enforced by the padding_mask inside CrossAttentionFusion which uses eff_len_flat as the effective prefix length. the causal structure in the SCANPATH ENCODER (step 2) is also needed — token t in scan_tokens already only sees fixations 0..t due to the causal mask.

**cost:** the tiling means CrossAttentionFusion and the decoder both run on B×T = 1920 items instead of B = 128. that's 15× more compute there, but the encoder (the bottleneck) only runs once. net speedup over the naive approach is significant.

## losses

**KL loss:**
- make a Gaussian heatmap centered at the target fixation (σ=2.0 in heatmap coords)
- KL(target || prediction) = sum over 4096 pixels of target × (log target - log pred)
- needs σ hyperparameter; sensitive to its choice

**NLL / ll loss (what I'm using now):**
- just: -log_pred[y_pixel, x_pixel] at the ACTUAL fixation location
- no Gaussian, no σ
- directly maximizes the log-probability of where the viewer actually looked
- much sharper gradient signal (only one pixel contributes per step)
- I map the normalized (x,y) → pixel index by: `col = round((x+1)/2 × 63)`, `row = round((y+1)/2 × 63)`, clamp to [0,63]

**why ll is better:** no nuisance hyperparameter, and the signal is cleaner — you're directly optimizing what you care about (high probability at the fixation). KL was essentially training the model to be "spread out" around the target location which is not what you want at test time.

**multi-step version:** for predict-all, I compute the loss over all valid steps and average:
```
valid_mask[b,t] = (t < fixations_len[b] - 1)
loss = mean of -ll over all valid (b,t) pairs
```

**what is a valid (b,t) pair?** step t for sample b is valid when fixation t+1 actually exists — i.e. `t < fixations_len[b] - 1`. a scanpath with 5 fixations contributes 4 valid steps (predict 1 from [0], predict 2 from [0,1], predict 3 from [0,1,2], predict 4 from [0,1,2,3]). steps 4–14 for that sample are masked out — the targets would be padding. we average only over valid pairs, so shorter scanpaths aren't penalised for missing predictions.

## metrics

**KL divergence:** lower is better. measures how well the predicted distribution matches the Gaussian heatmap. sensitive to the σ choice.

**NSS (Normalized Scanpath Saliency):** z-score the predicted probability map (mean=0, std=1 across all 4096 pixels), then read off the value at the target fixation location. 0 = the model puts exactly average probability there (uninformative). 1 = one std above average. higher = better. scale-invariant: multiplying the whole heatmap by a constant doesn't change NSS.

computed per prediction step, not per scanpath. we flatten all valid (b,t) pairs → (V, 64, 64) heatmaps and (V, 2) target coordinates, compute one NSS value per row, and average. a scanpath with L fixations contributes L-1 NSS values (one per valid prediction step), each treated independently. so the final NSS is an average over prediction steps across all samples, not over scanpaths.

DeepGaze III (state of the art on humans) gets ~6. my model at 200k images NLL, epoch 8 is around 4.43.

**AUC:** area under ROC curve treating fixation vs. non-fixation locations as a binary classification. 0.5 = random.

**ll (log-likelihood):** mean -NLL at fixation locations. higher (less negative) = better.

## training setup

- optimizer: AdamW, lr=3e-4, weight_decay=0.01
- lr schedule: cosine with 5% warmup (linear ramp up then cosine decay to 0)
- grad clip: 1.0 (by norm)
- AMP (mixed precision): float16 for forward, float32 for loss + grad
- cuDNN benchmark mode: lets CUDA pick the fastest conv kernel per shape; no determinism (didn't need it, and it was silently killing throughput)
- batch size: 128
- 15 epochs
- ~200k training images, paths_per_image=16

**why 3e-4?** standard starting point for AdamW with mixed precision; known to work well for transformers of this scale. cosine schedule will reduce it gracefully.

**why weight_decay=0.01?** lighter than the standard 0.05 for vision transformers — the encoder is frozen so we have much fewer parameters at risk of overfitting.

**visual scanpath features — how it works:** for each fixation at (x,y), we snap to the nearest patch index `idx = row*16 + col`, look up `image_tokens[b, idx]` (the adapted DINOv2 feature there), project it through a separate `Linear(256,256)`, and ADD it to the scanpath token before the transformer runs:

```
e_t = coord_proj(x_t, y_t) + pos_embed(t) + patch_feat_proj(image_tokens[b, idx_t])
```

the separate projection (rather than direct addition) lets the network learn to weight visual vs. coordinate information independently.

**what it's supposed to do:** the scanpath self-attention now operates over tokens that encode "I was at (x,y) AND saw [semantic content]" rather than just coordinates. this enables the transformer to learn relationships BETWEEN fixations based on visual content — "fixation 2 was on a face, fixation 5 was also on a face, they should attend to each other." as a side effect, when the fusion cross-attention queries these scanpath tokens, it can ask "where did the viewer look AND what did they see?" rather than just "where?"

**result:** didn't move the needle much. apparently the model already recovers the relevant visual context implicitly via fusion cross-attention. makes sense in retrospect — the image tokens flow into fusion anyway, so the cross-attention can already associate patches with fixation history.

## prefix encoding alternatives (to discuss with supervisor)

last meeting the feedback was "think about other ways to encode the prefix." what I've done: the visfeat ablation (above). what I'm thinking about for future:

**displacement encoding:** encode saccade vectors (Δx, Δy) = (x_t - x_{t-1}, y_t - y_{t-1}) instead of absolute positions. motivated by Tatler & Vincent (2009): saccade amplitude/direction biases account for a lot of variance in where people look, independently of image content. first fixation gets (0,0). could also do both (concatenate abs + Δ).
- *potential problem:* this data is synthetic from an active inference model — not guaranteed to have the same saccade statistics as humans.

**patch-index discretization:** quantize each fixation to the nearest 16×16 patch index → nn.Embedding(256, 256) instead of Linear(2, 256). removes the linearity assumption. each patch gets its own learned "identity" token. natural since the image side is already patch-indexed.
- *potential problem:* loses sub-patch precision (each patch is ~14px).

**Fourier features over coordinates:** expand (x,y) → [sin(2^k·π·x), cos(2^k·π·x), ...] before Linear projection. motivated by Tancik et al. (2020) / NeRF: MLPs struggle to learn high-frequency functions of raw low-dim inputs; Fourier features give the network direct access to high-frequency components.
- *potential problem:* the original motivation (NeRF, fitting individual images at pixel level) requires very fine spatial precision. fixation data is smooth and coarse — people don't land at high-frequency locations. the benefit of Fourier features only exists at frequencies relevant to the task; at the scales that matter (coarse patch-level), a linear layer already handles the distinction fine. so the theoretical motivation doesn't transfer cleanly here.

**explicit IOR prior:** render past fixations as a Gaussian inhibition map at heatmap resolution, subtract from output logits before softmax. motivated by Posner & Cohen (1984), Klein (2000): inhibition of return is one of the most robust findings in eye movement research.
- *potential problem:* the active inference data generator may already encode IOR intrinsically — adding an explicit prior could double-count it.

## profiler results

measured on A100, **realistic training conditions**: batch_size=128, seq_len=16 (T=15), fusion_layers=4, d_model=256, paths_per_image=16, NLL loss, AMP enabled. real model.forward() (no manual reimplementation), per-module forward/backward hooks with cuda.synchronize fences.

### per-module breakdown (real model.forward, ms/step)

```
module                  forward     backward     fwd+bwd
image_encoder            8.70 ms      0.00 ms     8.70 ms
image_adapter            0.20 ms      0.01 ms     0.21 ms
scanpath_encoder         2.37 ms      0.02 ms     2.38 ms
  fusion_0              16.38 ms     28.65 ms    45.03 ms
  fusion_1              16.36 ms     28.65 ms    45.01 ms
  fusion_2              16.35 ms     28.67 ms    45.02 ms
  fusion_3              16.36 ms     28.69 ms    45.05 ms
fusion (sum)            65.45 ms    114.67 ms   180.12 ms
decoder                 62.82 ms     91.14 ms   153.96 ms
```

### section-level wall-clock (ms/step, % of step)

```
target_heatmap          0.01 ms    0.0%   (NLL doesn't build Gaussian heatmaps)
zero_grad               0.20 ms    0.1%
forward_total         141.01 ms   39.7%
loss                    0.75 ms    0.2%
backward_total        210.78 ms   59.4%
optimizer               2.05 ms    0.6%
full step (with sync) 354.80 ms  100.0%
```

### what this means

- **backward is 59.4% of compute** — more than the entire forward pass. all 211 ms of backward lives in two places: fusion (115 ms = 54% of backward) and decoder (91 ms = 43%). everything else combined is < 3% of backward.

- **encoder forward only 8.7 ms (2.5% of step)** — `paths_per_image=16` optimization works exactly as expected. without it, DINOv2 would run on 128 images instead of 8, costing ~16× more (~140 ms = ~40% of step).

- **scanpath encoder is negligible (0.7% combined fwd+bwd)** — the 2-layer transformer over 15 tokens is essentially free. **I can experiment with much richer prefix representations (more layers, wider, displacement features, IOR, etc.) without any compute concern.**

- **the four fusion layers cost almost identically** (~16ms forward / ~29ms backward each). consistent with their identical structure. bidirectional fusion will roughly double per-layer time (extra MHA + extra FFN).

- **decoder is surprisingly expensive (62.8 ms forward + 91.1 ms backward = 154 ms)** — almost as much as all four fusion layers combined. this is because the decoder operates on the tiled B×T = 1920 items, running 4 conv layers + 2 upsamples each producing larger spatial tensors. the 32×32→64×64 upsample step in particular processes 1920×128 channels at 64×64 = a lot of pixels. **possible target for optimization: smaller decoder hidden_channels, or skipping the second upsample (predict at 32×32 instead of 64×64).**
